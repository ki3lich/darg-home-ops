# Accept Home Assistant `.storage` zero-length corruption as a power-loss recovery, not a pod-config bug

Home Assistant repeatedly surfaced repair issues for zero-length `.storage` files (`core.restore_state`, `bluetooth.passive_update_processor` — the latter twice). Root cause confirmed at the code level: HA's `Store` defaults to `atomic_writes=False`, so writes go through `homeassistant/util/file.py:write_utf8_file`, which writes a temp file and `os.replace`s it into place **without `os.fsync()` of the data first**. The directory entry is durable after the rename but the data may still sit un-flushed in the OS page cache. A process kill, SIGKILL, or pod restart cannot cause this — the page cache survives process death and the kernel writes it back — but a **power loss or hard node reset in the window between `os.replace` and the kernel flushing the data leaves the file at 0 bytes on next boot**. The months-apart cadence and the specific files hit (both write very frequently, maximizing the exposure window) match that. The action is therefore dismissal + cleanup, not a HelmRelease change: HA already auto-creates a valid default at the original path and renames the empty file to `…corrupt.<ts>`, so functionally nothing is broken; the empty file is unrecoverable data with nothing to restore. Real prevention is operational (UPS / graceful node shutdown so the host does not lose power mid-flush), not declarative — no change to the `home-assistant` HelmRelease can close HA's non-fsync write path.

## Considered options

- **Dismiss + cleanup (chosen):** Submit the two repair issues in the HA UI and delete the three zero-byte `…corrupt.*` files. Recovers nothing because there is nothing to recover (0 bytes), and HA never reads the renamed `.corrupt.*` files again. Accepts that the two stores lose their in-memory state on the rare power-loss event and are rebuilt from defaults; `restore_state` history and bluetooth passive-update cache are non-critical and regenerate.
- **Raise `terminationGracePeriodSeconds` / add a `preStop` flush hook (rejected as a fix for *this* bug):** Reasonable hardening for clean SIGTERM shutdowns, but does not address the cause — the corruption is from power loss, not graceful termination, and the page cache already survives SIGTERM. Pursue only as general good-practice, not as a remedy for the zero-length files.
- **Switch the affected stores to `atomic_writes=True` (rejected):** Would use `write_utf8_file_atomic`, which `fsync`s before rename — but it is HA core code, not configurable per-deployment, and upstream's default is non-atomic for write-throughput reasons. Not actionable from this repo.
- **Move `/config` off `openebs-hostpath` to a network-backed storage class (rejected):** Would not help; the durability gap is before the data reaches the filesystem (page cache vs power), and a network PV adds a new loss surface. The `openebs-hostpath` 5Gi RWO PVC is not the cause.
